This playbook is the quality assurance and test engineering guide for QA Engineers and SDETs on HelloSmart.

As a QA Engineer on HelloSmart, your primary mission is to protect **tenant isolation**, guarantee **workspace security**, and ensure **flawless candidate examination experiences**.

---

## 1. Test Architecture Matrix

HelloSmart organizes testing into four automated tiers to balance rapid feedback in CI with comprehensive end-to-end coverage:

| Testing Tier | Verification Focus | Tooling | Execution Trigger |
|---|---|---|---|
| **Multi-Tenant Isolation** | Row-Level Security enforcement, cross-tenant 404 assertions (`BR-01`) | Vitest, PostgreSQL test containers | Every pull request and commit |
| **Contract Validation** | OpenAPI 3.1 specifications and shared Zod schemas (`@hs/contracts`) | Prism, Zod | Every pull request |
| **Service Integration** | Workspace container orchestration, AI proxy token quotas, BullMQ queues | Vitest, Docker local mock | Hourly CI and Nightly runs |
| **End-to-End (E2E)** | Candidate portal, fullscreen tracking, review workflows, billing webhooks | Playwright, Chromium | Pre-merge verification and Nightly |

## 2. Multi-Tenant Isolation Testing (BR-01)

The foundation of enterprise trust in HelloSmart is **strict tenant isolation**. Data belonging to Organization A must never be accessible, visible, or inferable by Organization B.

### The 404 Invariant Rule
When a user belonging to Organization A requests a resource ID that belongs to Organization B, the API **must return HTTP 404 Not Found**, never HTTP 403 Forbidden.

Returning a 403 leaks that the identifier exists inside another company's account. Returning 404 preserves complete opacity.

### Running Tenancy Suites
```bash
# Execute the automated cross-tenant test suite
pnpm test:tenancy
```

### Authoring a Multi-Tenant Test Case
```typescript
import { describe, it, expect } from 'vitest';
import { createTenantContext, testClient } from '@hs/fixtures';

describe('BR-01: Cross-Tenant Resource Isolation', () => {
  it('returns 404 when Org B queries a candidate created by Org A', async () => {
    // 1. Provision two distinct isolated tenant contexts
    const orgA = await createTenantContext('acme-corp');
    const orgB = await createTenantContext('beta-industries');
    
    // 2. Create candidate Jane Doe inside Org A
    const candidateA = await orgA.createCandidate({ 
      name: 'Jane Doe',
      email: 'jane@example.com' 
    });

    // 3. Attempt to fetch Jane Doe using Org B authenticated session
    const response = await testClient(orgB.sessionToken)
      .get(`/api/v1/candidates/${candidateA.id}`);

    // 4. Assert HTTP 404 with RFC 7807 Problem Details payload
    expect(response.status).toBe(404);
    expect(response.body).toEqual({
      type: 'https://hellosmart.ai/problems/not-found',
      title: 'Not Found',
      status: 404,
      detail: 'Candidate not found',
    });
  });
});
```

## 3. Playwright End-to-End Testing

End-to-end tests live in `tests/e2e/` and simulate realistic candidate and administrator browser interactions:

```bash
# Run headless browser test suite
pnpm test:e2e

# Run with interactive Playwright UI runner
pnpm --filter @hs/e2e test:ui
```

### Critical Examination Flows to Verify
1. **First-Login Password Reset (BR-24)**: Asserts that an invited candidate with `must_reset_password = true` cannot navigate to the dashboard until they submit a new password.
2. **Consent Screen Gate (BR-12)**: Asserts that the "Connect to Workspace" button is strictly disabled until the candidate reviews and accepts the recording consent checkbox.
3. **Fullscreen Disconnect Detection (BR-10)**: Simulates exiting browser fullscreen (`document.exitFullscreen()`). Asserts that the terminal session is immediately disconnected, logs a `fullscreen_exit` telemetry event, and displays the modal resume overlay.
4. **Auto-Submit on Timer Expiry (BR-08)**: Simulates backend deadline expiration. Asserts that the orchestrator creates a final snapshot, marks the assignment as `auto_submitted`, and closes the session.
5. **Spend Cap Warning and Hard Rejection (BR-15)**: Sends simulated prompt traffic exceeding candidate budget caps, verifying that candidate chat displays a spend cap warning followed by a friendly rate limit block.

## 4. Tamper-Evident Audit Chain Verification (BR-31)

All high-privilege mutations generate an append-only audit log row in `audit.events`:
- Organization provisioning, status modifications, and suspensions
- Entitlement quota changes (template counts, candidate caps)
- Candidate creation, deletion, or score releases
- AI provider key creations or updates (recording only the last 4 digits)

The QA suite verifies the cryptographic SHA-256 hash chain:
```
hash_n = SHA256(hash_(n-1) || row_payload_n)
```
Any simulated row deletion, update, or out-of-order insertion must immediately fail hash chain verification and raise a security alarm.

## 5. Performance and Resilience Benchmarks

Every release candidate is tested against these operational benchmarks:
- **Workspace Launch Latency**: Warm container connect time must be &le; 15 seconds from candidate click to interactive terminal.
- **Continuous Snapshot Recovery (BR-11)**: Simulated container crashes must restore file diffs, git commits, and terminal history with recovery point objective (RPO) &le; 30 seconds.
- **WebSocket Reconnection**: Temporary network drops must auto-reconnect within 5 seconds without resetting session timers.

## 6. QA Definition of Done (DoD) and Release Sign-Off

Before signing off on any release branch (`dev` to `qa`, or `qa` to `main`):
1. Multi-tenant isolation test suite passes with zero failures (`pnpm test:tenancy`).
2. All Playwright browser test suites pass across Chrome and Firefox (`pnpm test:e2e`).
3. Cryptographic audit chain validation succeeds on sample seed mutations.
4. Contract compliance is confirmed with Prism mock server (`pnpm contracts:check`).
5. Zero documentation drift is verified (`pnpm docs:sync-check`).
