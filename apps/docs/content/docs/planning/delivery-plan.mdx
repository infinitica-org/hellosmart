Why a shared host pool (D-11): candidates need what feels like a real Linux box with Docker, dev servers and coding agents (the bar Outship sets). A Sysbox system container gives each candidate exactly that, while several candidates share one host:
- **Cost:** warm capacity is paid per slot, not per VM. An idle pool of 2 hosts covers 8–12 instant starts.
- **Speed:** a slot starts in seconds (image already on the host), well inside p95 < 60 s.
- **Isolation:** Sysbox runs every container in a separate user namespace (root inside is unprivileged on the host). Each slot also has its own network namespace and egress rules, hard cgroup limits and its own disk quota. Candidates can't see each other's files, processes or traffic.
- **Escape hatch:** GPU, heavy or unusual templates set `isolation: dedicated` and get a full VM through the same orchestrator API. Nothing else changes.

Options considered and rejected: one VM per candidate (strongest isolation, but 3–4× the idle cost and slower starts); plain Docker or systemd users on a shared VM (too weak for untrusted code, and Docker-in-Docker would need privileged mode); Firecracker microVMs (best isolation, but EC2 needs metal instances for it and it's too much build effort before 12 Dec; revisit in Phase 2).

### 3.3 Reliability and security

- Multi-AZ for ALB, ECS (min 2 tasks per service), Aurora, Redis. Target 99.5% (stretch 99.9%).
- Aurora PITR 14 days, S3 versioning, weekly restore drill from S6.
- RLS: every request sets `app.org_id` on the connection; tenant tables have policy `org_id = current_setting('app.org_id')`. Defence in depth with repository-level scoping.
- Idempotency: `Idempotency-Key` header on mutations, unique `gateway_ref` for payments, dedupe IDs on SQS.
- Auto-submit: EventBridge one-shot schedule per assignment + 1-minute sweeper as backup.
- Secrets never leave Secrets Manager except into the proxy process memory. CI scans for secrets (gitleaks) on every PR.
- WAF managed rules + rate limits on `/auth/*`. GuardDuty, Security Hub, Inspector on.
- Workspaces: one Sysbox slot per candidate on shared hosts; slots cannot reach instance metadata, host network or other slots; hosts use IMDSv2 and have no role with data access; per-slot egress allowlist; AI domains blocked when AI OFF; slots destroyed at session end, hosts recycled every 24 h.

## 4. Reviewer agents and rubrics

### 4.1 Agent definition (versioned config in the agent library)

```yaml
id: debugging-process
version: 1.0.0
model: claude-sonnet-5-5
evidence_channels: [terminal_log, git_timeline, ai_transcript]
scale: {min: 1, max: 5}
anchors:
  1: "Random edits, no hypothesis, accepts AI output blindly"
  3: "Forms hypotheses, tests some, partial verification"
  5: "Systematic: reproduce > isolate > fix > verify, catches AI mistakes"
signals: [reproduces bug, reads logs, writes failing test, verifies fix]
red_flags: [disables tests, hardcodes expected output]
output: {score, confidence, rationale, evidence: [{ref, quote}], flags}
```

A company `RubricItem` points at a library agent and overrides goal, anchors, weight and red flags. Weights must total 100.

### 4.2 Launch agent library (10)

| Agent | Evidence | Measures |
|---|---|---|
| Task completion | deliverables, hidden tests, brief | Acceptance criteria met |
| Code quality | final diff | Structure, readability, idioms |
| Debugging process | terminal, git timeline | Systematic reproduce > fix > verify |
| AI collaboration | AI transcript, diff | Steering the agent, catching its mistakes, not blind paste |
| Problem decomposition | timeline, transcript | Planning and ordering |
| Testing discipline | diff, test runs | Tests written/run, coverage of edge cases |
| Communication | written deliverables, chat | Clarity and audience fit |
| Business reasoning | Chat deliverables | Assumptions, trade-offs, numbers correct |
| Domain correctness | deliverables + template answer key | Factual and domain accuracy |
| Integrity observer | activity events | **Flags only, never scores** |

### 4.3 Review pipeline (Step Functions)

1. **Evidence builder**: turns raw artifacts into a bounded evidence bundle; every chunk gets a stable `ref` (`term:00412`, `diff:src/app.ts#L20-40`, `ai:msg-17`).
2. **Sanitizer**: wraps candidate content in untrusted delimiters, strips grader-directed instructions, runs an injection classifier. A hit adds `suspected_injection` and forces low confidence.
3. **Agent runs**: Map state, one run per rubric item, parallel, no shared context, retries ×2.
4. **Validator**: every score must have ≥1 resolvable `ref`; otherwise one retry, then the dimension is marked `missing`.
5. **Aggregator** (deterministic code): weighted overall, disagreement flag (related agents spread ≥ 2 points or confidence < 0.5), report JSON.
6. Review moves to `agent_report_ready`; company notified. SLA < 15 min.

**Quality gate:** every template ships 5 golden submissions (strong, good, average, weak, adversarial). An agent version publishes only if it scores within ±0.5 of the human labels and the adversarial one does not move scores. This doubles as the BR-18 injection suite and runs in CI nightly.

## 5. Templates and virtualization

### 5.1 Manifest (one JSON-schema-validated file per template version)

```yaml
template: backend-incident-debug
version: 1.0.0
mode: cloud                      # cloud | chat
runtime:
  image: Dockerfile              # built to ECR on publish, pre-pulled on hosts
  size: medium                   # small | medium | dedicated
  isolation: shared              # shared (Sysbox slot) | dedicated (own VM)
  services: compose.yaml         # postgres, redis, localstack...
  coding_agents: [claude-code, codex]       # preinstalled, pointed at AI proxy
repo: {source: github, ref: <commit>}       # cloned into fresh repo, no history leak
seed: seed/
env_slots: [{name: PAYMENT_SANDBOX_KEY, secret: true, required: false}]
ai_defaults: {enabled: true, models: [claude-sonnet-5-5], cap_usd: 5, rpm: 20}
brief: brief.md
deliverables: [{path: NOTES.md}, {hidden_tests: "pnpm test:hidden"}]
reviewers: [task-completion, debugging-process, ai-collaboration, code-quality]
golden_submissions: golden/
timing_default: {type: duration, duration_minutes: 120}
```

### 5.2 Virtualization: shared host pool

**Host:** `m7i.2xlarge` (8 vCPU, 32 GB), Ubuntu, Sysbox, 200 GB gp3, built from one Packer golden AMI that pre-pulls every published template image. Nothing on the host can reach the prod DB.

**Slot sizes** (set per template in the manifest `runtime.size`):

| Size | Limits | Slots per host | Use |
|---|---|---|---|
| `small` | 1 vCPU, 4 GB, 15 GB disk | 6 | Scripts, single service, data notebooks |
| `medium` (default) | 2 vCPU, 6 GB, 25 GB disk | 4 | App + DB + Redis via compose, coding agent |
| `dedicated` | whole VM (`t3.xlarge` or as declared) | 1 | Heavy builds, GPU, special kernels |

CPU is soft-shared (cgroup weights, ~1.3× overcommit allowed). Memory and disk are hard limits, so one candidate can never take memory from another.

**Flow:**
1. Template publish > CI builds the template **container image** (Dockerfile from the manifest) and pushes to ECR. The host AMI is rebuilt nightly to pre-pull it; until then hosts pull on first use.
2. Smoke test (AD-013): orchestrator starts one slot on the QA AWS host (Sysbox), runs health checks + golden-submission hidden tests, tears down. Must pass before `published`.
3. Terraform module `workspace_hosts`: Auto Scaling group with a **free-slot target**: keep ≥ 8 free `medium` slots (configurable in admin), scale out when free slots drop below target, scale in only empty hosts.
4. **Scheduler (orchestrator):** bin-packs new sessions onto the fullest host that fits (frees whole hosts for scale-in), never two slots of the same candidate on one host, and spreads across 2 AZs.
5. **Connect:** create Sysbox container from the template image > own network namespace with an egress allowlist (AI domains blocked when AI is OFF) > inject per-session env from SSM (deleted at end) > start compose services inside > issue proxy token > `ws-agent` begins autosave. Target < 20 s.
6. Browser connects through the authenticated `ws-gateway` to that slot's code-server and terminal. No public IPs. A session token is bound to one slot.
7. **Autosave:** the slot's workspace lives on its own quota'd directory; `ws-agent` pushes a git snapshot + terminal log to S3 every 15 s (RPO ≤ 30 s). If a host dies, resume rebuilds the slot on another host from the last snapshot.
8. **End:** final snapshot to S3, container and its volume destroyed, slot returned to the pool. Hosts are recycled after 24 h for hygiene.

**Noisy-neighbour controls:** hard memory/disk/PID limits, I/O weights, per-slot network bandwidth caps, CloudWatch per-slot metrics. If a slot hits limits repeatedly it's logged as an activity event for reviewers (evidence, not a penalty) and the host stops taking new sessions until load drops.

**Capacity guide:** 1 host ≈ 4 concurrent candidates (medium). 100 concurrent candidates ≈ 25 hosts + warm buffer. Launch-week budget is set by the AWS Budgets alarm in the `workspaces` account.

Chat workspace: no VM. Next.js page + ai-proxy + files from S3.

## 6. AI-SDLC: how we build with agents

Engineers do not hand-write features. Every engineer runs coding agents (Claude Code, Codex or equivalent) in parallel. Humans own **intent, contracts, review and acceptance**. This section is the operating system for that.

### 6.1 Principles

1. **Contract before code.** Agents build against frozen contracts (OpenAPI, DB schema, events, UI routes). This is what removes cross-team blocking.
2. **Small, verifiable units.** One ticket = one requirement ID slice = one PR ≤ ~600 changed lines, with tests.
3. **Agents verify themselves.** No PR without passing tests, typecheck, lint, and the agent's own self-review against acceptance criteria.
4. **Humans are the gate.** Every merge needs one human approval from the owning department plus an AI review. Security-sensitive paths (Section 6.6) need the Architecture department.
5. **Context is code.** Agent instructions live in the repo and are versioned like code.

### 6.2 Lifecycle stages

| Stage | Who/what | Output | Gate |
|---|---|---|---|
| 1. Intake | Product Delivery | Zoho item with requirement ID, acceptance criteria copied from AGENTS.md | Ready checklist |
| 2. Task brief | Owning dept, assisted by agent | `tasks/<ID>.md`: goal, contract refs, files in scope, test plan, out-of-scope | Dept lead approves brief |
| 3. Contract | Architecture (only if contract changes) | PR to `packages/contracts` | Architecture approves; contract PRs merge first, daily |
| 4. Build | Engineer + parallel agents in git worktrees | Code + tests on branch `feat/<ID>-slug` | CI green |
| 5. Self-verify | Agent | Runs tests, checks each acceptance criterion, writes PR description with evidence | Checklist complete |
| 6. AI review | Review agent in CI | Correctness, tenancy, secrets, BR-rule check comments | No unresolved high findings |
| 7. Human review | Owning dept (+ Architecture for sensitive paths) | Approval | 1–2 approvals |
| 8. Preview | CI | Ephemeral env per PR in `dev` account | Smoke E2E green |
| 9. Merge to `dev` + QA | Squash-merge to `dev`, auto-deploy to QA AWS host | Feature flag off by default | QA smoke green |
| 10. QA | QA dept + test agents | Test run report in Zoho | Sprint QA sign-off |
| 11. Prod | Release Monday | Flags enabled per plan | Go/no-go checklist |
| 12. Learn | All | Prompt/agent-rule fixes into `AGENTS.md` / module `CLAUDE.md` | Retro action items |

### 6.3 Repository context for agents

- Root [AGENTS.md](../AGENTS.md): product rules (exists).
- `CLAUDE.md` (root): repo commands, conventions, links to the files below.
- `apps/*/CLAUDE.md` and `services/*/CLAUDE.md`: module rules, patterns, "how to add an endpoint/page/agent".
- `packages/contracts/`: OpenAPI spec, Zod schemas, event schemas, DB schema: the single source agents build against.
- `tasks/`: one brief per ticket.
- `.claude/` (shared): slash commands such as `/new-endpoint`, `/new-page`, `/cross-tenant-test`, `/new-agent`, `/new-template`; hooks that run typecheck + tests after edits and block commits containing secrets.
- `docs/adr/`: architecture decision records; agents must read relevant ADRs before changing a module.

### 6.4 Parallel-agent working rules

- Each engineer runs 2–4 agents concurrently, each in its own **git worktree** on its own ticket. Never two agents on the same files.
- Module ownership via `CODEOWNERS`; an agent may only edit files in its department's paths plus tests. Cross-module needs = contract request, not a direct edit.
- Generated code follows existing patterns; agents must reuse `packages/*` utilities (no parallel helpers).
- Mandatory in every PR an agent opens: requirement ID in title, tests named after IDs/BRs, cross-tenant test for any new endpoint, migration with `org_id` + index if tables change.
- Agents never touch: `infra/prod`, secrets, `packages/contracts` (except Architecture), CI workflows (except Architecture/DevOps).

### 6.5 Quality automation (every PR)

typecheck · lint · unit · integration (Testcontainers Postgres/Redis) · cross-tenant suite · contract conformance (API responses vs OpenAPI) · gitleaks · dependency audit · AI code review · Playwright smoke on preview env · bundle size budget.
Nightly: full E2E, agent golden-set evaluation, injection suite, load test from S5.

### 6.6 Sensitive paths (extra human approval from Architecture)

`auth/`, `tenancy/`, `rbac/`, `billing/`, `ai-proxy/`, `reviewer/sanitizer`, `orchestrator/`, `infra/`, any migration, consent text, retention jobs.

### 6.7 Metrics we track weekly

PR lead time, PRs merged per engineer, CI pass rate first try, escaped defects per sprint, agent rework rate (PRs needing > 2 review rounds), AI spend per department.

## 7. Working without blocking each other

Blocking is removed structurally, not by coordination.

| Mechanism | How it unblocks |
|---|---|
| **Contracts frozen in S0** | OpenAPI, DB schema, event schemas and UI route map are merged by Fri 30 Oct. Every department builds against them from day one. |
| **Mock server from contracts** | `pnpm mock` serves the OpenAPI spec (Prism) with realistic fixtures. Frontend never waits for backend. |
| **Fake adapters for every external** | `FakePaymentGateway`, `FakeEmail` (writes to local inbox UI), `FakeLLM` (deterministic), `FakeWorkspaceRuntime` (local docker), LocalStack for AWS. No department waits for credentials. |
| **Seed + fixtures package** | Shared `packages/fixtures`: two orgs, admin, candidates, templates, submissions in every state. Reviewer and UI work start before real sessions exist. |
| **Feature flags** | Incomplete work merges to trunk behind flags; nothing waits for "the whole feature". |
| **Trunk-based, daily merges** | No long branches; conflicts surface in hours, not weeks. |
| **Contract change SLA** | Contract change requests answered by Architecture within 4 working hours; additive changes only after freeze. |
| **Department-owned paths** | CODEOWNERS means no one needs another department to edit their code. |
| **Async daily** | 10-minute written standup in Zoho/chat; one 15-min call only for blockers. |

Dependency rule: **a ticket may depend only on a contract, never on another department's implementation.** Integration happens on the QA environment every Wednesday.
